# API v1 — Цены по задачам и скидка на заказ

**Кому:** разработчикам мобильных приложений (Client + Master)
**Тип изменения:** в основном аддитивное — эндпоинты и поля не удалены,
но у Client **сменился тип `final_price`** (строка → число), см. §2.2
**Статус:** изменения на бэкенде, релиз согласовать с выкаткой приложений

---

## Что случилось

Раньше стоимость заказа была **одним числом**: администратор вручную вбивал `final_price`
в админке. Теперь стоимость складывается **из цен отдельных задач** (`tasks`), а на весь заказ
можно дать **скидку в процентах**.

```
final_price = сумма цен задач − скидка
```

Пересчёт полностью на бэкенде: как только админ меняет цену любой задачи или процент скидки,
`final_price` заказа пересчитывается сам. Приложениям **ничего считать не нужно** — только
показывать. Но если хотите показать разбивку («работы 500, скидка 10% = 50, итого 450»), для
этого добавлены готовые поля.

---

## Насколько это ломает приложения

| Приложение | Степень |
|---|---|
| **Master** | Не ломается. Добавлены `price` у задачи, `discount_percent` и `tasks_total` у заказа |
| **Client** | Ломается в одном месте: `final_price` теперь **число**, а не строка. Плюс добавлены `price` у задачи, `discount_percent`, `tasks_total`, `discount_amount` у заказа |

Новые ключи старые сборки просто проигнорируют. Единственное, что реально может уронить
приложение, — парсинг `final_price` в Client: если он написан как `double.parse(json['final_price'])`,
на числе будет исключение.

> **Главный риск — Dart null-safety и типы чисел.** Читайте раздел «Типы в JSON» ниже, там
> два неочевидных места, на которых парсер падает.

## 1. Новые поля

### Задача (`tasks[]`) — Master и Client

| Поле | Тип в JSON | Nullable | Значение |
|---|---|---|---|
| `price` | number | **да** | Цена этой задачи. `null` — цена ещё не назначена админом |

### Заказ — Master

| Поле | Тип в JSON | Nullable | Когда приходит |
|---|---|---|---|
| `discount_percent` | number | нет (по умолчанию `0`) | Всегда |
| `tasks_total` | number | **да** | Только там, где приходит `tasks` (см. таблицу в §3) |

### Заказ — Client

| Поле | Тип в JSON | Nullable | Когда приходит |
|---|---|---|---|
| `discount_percent` | number | нет (по умолчанию `0`) | Всегда |
| `tasks_total` | number | **да** | Только там, где приходит `tasks` (см. таблицу в §3) |
| `discount_amount` | number | нет | Только там, где приходит `tasks` (см. таблицу в §3) |

**Смысл полей:**

- `tasks_total` — сумма цен задач **до скидки**. Задачи без цены в сумму не входят.
  Если **ни у одной** задачи цены нет — `tasks_total = null` и `final_price = null`.
- `discount_amount` — сколько денег снимает скидка: `round(tasks_total × discount_percent / 100, 2)`.
- `final_price` — **итог к оплате**, уже со скидкой. Поле старое, изменился только источник:
  раньше его вбивали руками, теперь считает бэкенд.

```
tasks_total     500.00   ← сумма цен задач
discount_percent    10
discount_amount  50.00   ← 500 × 10%
final_price     450.00   ← это показывать клиенту как «к оплате»
```

> В приложении Master поля `discount_amount` нет — считайте `tasks_total − final_price`,
> либо запросите его у бэкенда (см. §7).

## 2. Типы в JSON — читать обязательно

### 2.1. Числа могут прийти как `int` и как `double`

`300` придёт как `300`, а `150.25` — как `150.25`. В Dart `jsonDecode` в первом случае вернёт
`int`, во втором `double`, и приведение `json['price'] as double` **упадёт** на целой цене.

```dart
// ❌ упадёт на price = 300
final double? price = json['price'] as double?;

// ✅
final double? price = (json['price'] as num?)?.toDouble();
```

Касается: `price`, `tasks_total`, `discount_amount`, `discount_percent`, `final_price` (у Master).

### 2.2. ⚠️ `final_price` у Client сменил тип: строка → число

Было расхождение: Master отдавал `450.25`, Client — `"450.25"`. Расхождение убрано,
**теперь везде число**.

| Эндпоинт | Было | Стало |
|---|---|---|
| `GET /api/v1/master/orders/{id}` | `450.25` | `450.25` — без изменений |
| `GET /api/v1/client/orders/*` | `"450.25"` | `450.25` — **изменилось** |

```dart
// ❌ теперь упадёт: "type 'double' is not a subtype of type 'String'"
final finalPrice = double.parse(json['final_price'] as String);

// ✅
final double? finalPrice = (json['final_price'] as num?)?.toDouble();
```

Касается всех клиентских эндпоинтов заказа: список, детали, создание, обновление, отмена.

### 2.3. Отсутствующий ключ ≠ `null`

`tasks_total`, `discount_amount` и `tasks` **отсутствуют в JSON целиком** на тех эндпоинтах,
где задачи не подгружаются. Не `null`, а ключа нет. `json['tasks_total']` вернёт `null` —
но отличить «нет данных» от «нет цен» по этому полю нельзя. Ориентируйтесь на таблицу §3:
разбивку по деньгам показывайте только на экране деталей заказа.

## 3. Где какие поля приходят

### Master

| Эндпоинт | `discount_percent` | `tasks_total` | `tasks[]` c `price` |
|---|---|---|---|
| `GET /master/orders` (список) | ✅ | ❌ нет ключа | ❌ нет ключа |
| `GET /master/orders/{id}` | ✅ | ✅ | ✅ |
| `POST /master/orders/{id}/start` | ✅ | ✅ | ✅ |
| `POST /master/orders/{id}/complete` | ✅ | ✅ | ✅ |
| `POST /master/orders/{id}/tasks` (201) | — | — | ✅ одна задача, `price` всегда `null` |
| `POST /master/orders/{id}/tasks/{task}/photo` (202) | — | — | ✅ одна задача, с `price` |

> `start` и `complete` возвращают заказ в том же полном виде, что и `GET /master/orders/{id}`
> — с задачами и суммами. Перезапрашивать заказ после смены статуса не нужно.

### Client

| Эндпоинт | `discount_percent` | `tasks_total` / `discount_amount` | `tasks[]` c `price` |
|---|---|---|---|
| `GET /client/orders` (список) | ✅ | ❌ нет ключа | ❌ нет ключа |
| `GET /client/orders/{id}` | ✅ | ✅ | ✅ |
| `POST /client/orders` (создание) | ✅ | ❌ нет ключа | ❌ нет ключа |
| `PATCH /client/orders/{id}` | ✅ | ❌ нет ключа | ❌ нет ключа |
| `POST /client/orders/{id}/cancel` | ✅ | ❌ нет ключа | ❌ нет ключа |

## 4. Примеры ответов

### 4.1. `GET /api/v1/master/orders/{id}`

**Было:**

```json
{
  "data": {
    "id": 15,
    "status": "in_progress",
    "final_price": null,
    "tasks": [
      { "id": 41, "title": "Замена смесителя", "description": "Кухня" }
    ]
  }
}
```

**Стало:**

```json
{
  "data": {
    "id": 15,
    "status": "in_progress",
    "final_price": 450.25,
    "discount_percent": 10,
    "tasks_total": 500.28,
    "tasks": [
      {
        "id": 41,
        "title": "Замена смесителя",
        "description": "Кухня",
        "price": 300,
        "before_photos": [],
        "after_photos": []
      },
      {
        "id": 42,
        "title": "Прочистка сифона",
        "description": null,
        "price": 200.28,
        "before_photos": [],
        "after_photos": []
      }
    ]
  }
}
```

Задача без назначенной цены:

```json
{ "id": 43, "title": "Осмотр", "description": null, "price": null }
```

### 4.2. `GET /api/v1/client/orders/{id}`

**Стало** (фрагмент, только денежная часть):

```json
{
  "data": {
    "id": 15,
    "status": "in_progress",
    "final_price": 800,
    "discount_percent": 20,
    "tasks_total": 1000,
    "discount_amount": 200,
    "tasks": [
      {
        "id": 41,
        "title": "Замена смесителя",
        "description": "Кухня",
        "price": 1000,
        "before_photos": [
          { "id": 1, "url": "https://...", "status": "done" }
        ],
        "after_photos": []
      }
    ]
  }
}
```

Новое в `tasks[]` для Client: помимо `price` теперь приходит и `description` (раньше его
в клиентском ресурсе не было).

**Breaking для Client:** поля `before_photo_url`, `after_photo_url`, `before_status` и
`after_status` удалены. Вместо них — массивы `before_photos` / `after_photos` того же
формата, что и в мастерском API: `{ "id": int, "url": string, "status": string }`, до двух
фото на тип. Пустой массив, если фото нет.

## 5. Кто и как назначает цену

**Цену задачи и скидку выставляет администратор в веб-админке.** В мобильном API v1
эндпоинтов для этого нет:

- `POST /api/v1/master/orders/{id}/tasks` принимает только `title` и `description`.
  Поле `price` в теле запроса **игнорируется** — созданная задача всегда возвращает `price: null`.
- Эндпоинта «изменить цену задачи» и «поставить скидку» в мобильном API **нет**.

То есть для обоих приложений цены — **read-only**. Мастер создаёт задачи со своего телефона,
админ проставляет им цены, мастер и клиент видят обновлённые суммы при следующем
`GET /orders/{id}`.

> Если по бизнес-логике цену должен ставить мастер на месте — этих эндпоинтов не хватает,
> нужно ставить задачу бэкенду отдельно (см. §7).

## 6. Что сделать в приложениях

### Master

- [ ] Добавить `price` (nullable, `num → toDouble()`) в модель задачи.
- [ ] Добавить `discount_percent` и `tasks_total` (nullable) в модель заказа.
- [ ] На экране заказа показывать цену каждой задачи; для `price == null` — плейсхолдер
      («цена не назначена»), а не `0`.
- [ ] Показывать итог: `tasks_total` → скидка → `final_price`.
- [ ] Ответы `start` / `complete` можно класть прямо в состояние экрана — они полные.
- [ ] Не давать редактировать цену в UI — эндпоинта нет.

### Client

- [ ] Добавить `price` (nullable) и `description` в модель задачи.
- [ ] Добавить `discount_percent`, `tasks_total`, `discount_amount` в модель заказа.
- [ ] На экране деталей заказа показывать разбивку: работы → скидка → к оплате.
- [ ] В списке заказов разбивки нет — показывать только `final_price`.
- [ ] **Обязательно** переписать парсинг `final_price`: теперь это число, а не строка (§2.2).
- [ ] **Обязательно** переписать модель фото задачи: `before_photo_url` / `after_photo_url` /
      `before_status` / `after_status` удалены, вместо них массивы `before_photos` /
      `after_photos` (§4.2). Раньше эти поля всегда приходили `null` / `pending` — фото
      давно лежат в отдельной таблице.

### Обоим

- [ ] Все денежные поля парсить как `(json[...] as num?)?.toDouble()`.
- [ ] Все денежные поля объявить nullable (`double?`), кроме `discount_percent`.
- [ ] Проверить кейс «заказ завершён, но ни одной цены нет»: `final_price = null`,
      `tasks_total = null`. UI не должен показывать `0` как «бесплатно».

## 7. Что НЕ изменилось

- Ни один эндпоинт не удалён и не переименован.
- Структура `tasks[]` та же, добавлены только новые ключи.
- Загрузка фото задач (`POST /orders/{id}/tasks/{task}/photo`) — без изменений.
- Статусы заказа и переходы между ними — без изменений.
- Авторизация (OTP → Sanctum Bearer) — без изменений.
- Поле `final_price` осталось на месте с тем же смыслом «итог к оплате» (изменился только
  его тип у Client и способ расчёта на бэкенде).
- Координаты `client_lat` / `client_lng` у Client по-прежнему приходят **строками** —
  здесь ничего не трогали.

## 8. Вопросы к бэкенду

1. Появится ли `discount_amount` в ответах Master? Сейчас его приходится считать вычитанием.
2. Планируются ли эндпоинты «мастер ставит цену задачи»? Если да — когда, чтобы заложить UI.
3. Будут ли `tasks_total` / `discount_amount` в списках заказов, или разбивка навсегда только
   на экране деталей?
4. Есть ли реалтайм-уведомление об изменении цены, или приложению нужно поллить `GET /orders/{id}`?
5. `client_lat` / `client_lng` у Client тоже привести к числам, раз уж `final_price` привели?
